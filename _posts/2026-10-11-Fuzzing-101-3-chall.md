# Fuzzing101 3문제 클리어: Xpdf, tcpdump, LibTIFF 크래시 분석

이번 실습의 목표는 단순히 AFL++ 화면에서 `crashes` 숫자를 보는 것이 아니었다. 환경을 직접 만들고, 타깃과 버전을 의심해 보고, crash를 디버거와 sanitizer로 분류하고, 마지막에는 패치 빌드에 같은 PoC를 다시 넣어 보는 데까지를 완료 기준으로 잡았다.

최종 완료한 문제는 [Fuzzing101](https://github.com/antonio-morales/Fuzzing101)의 Exercise 1(Xpdf), Exercise 3(tcpdump), Exercise 4(LibTIFF)다. 원 과정은 Ubuntu 20.04.2에서 테스트되었지만 내 환경은 WSL2 Ubuntu 24.04.3이었다. 이 차이는 생각보다 중요했다.

## 환경 구축

WSL에는 GCC, make, git, GDB는 있었지만 clang, AFL++, LCOV가 없었고 `sudo`는 비밀번호를 요구했다. 그래서 Ubuntu의 AFL++ 4.09c 패키지를 사용자 디렉터리에 추출하고 `AFL_PATH`를 지정했다. `afl-gcc`로 smoke test를 빌드해 계측이 실제 동작하는 것도 확인했다.

tcpdump 빌드 중에는 `flex → m4`, `bison → BISON_PKGDATADIR`, `flex link test → libfl` 의존성이 차례로 드러났다. 필요한 패키지를 모두 사용자 디렉터리에 추출해 관리자 권한 없이 해결했다.

AFL++ 공식 문서는 source-only 빌드와 Docker 경로를 모두 제공한다. 이 실습에서는 Docker 엔진이 준비되지 않았으므로 로컬 패키지 추출을 택했다. 참고: [AFL++ INSTALL](https://github.com/AFLplusplus/AFLplusplus/blob/stable/docs/INSTALL.md).

## 1단계 — Xpdf, 공식 seed에서 AFL crash 찾기

Exercise 1은 PDF 파서인 Xpdf 3.02를 대상으로 한다. `pdftotext`를 AFL++의 GCC 래퍼로 계측하고 작은 PDF를 seed로 넣었다.

```bash
afl-fuzz -i seeds -o out -s 123 -- pdftotext @@ output.txt
```

10분 결과는 150,237 exec, 새 corpus 896개, crash 0개, timeout 3개였다. 중요한 점은 timeout 3개를 곧바로 취약점이라고 부르지 않은 것이다. 대표 timeout을 GDB로 실행하자 손상된 PDF 오류를 출력하고 정상적으로 종료했다. 20ms라는 짧은 AFL timeout 때문에 느린 입력이 hang으로 분류된 경우였다.

반면 공개 CVE PoC를 실행하면 SIGSEGV가 발생했고 GDB stack에서 `Parser::getObj()`가 반복되었다.

```text
Parser::getObj → Parser::makeStream → Dict::lookup
→ Object::fetch → XRef::fetch → Parser::getObj → ...
```

NVD는 [CVE-2019-13288](https://nvd.nist.gov/vuln/detail/CVE-2019-13288)을 `Parser::getObj()`의 무한 재귀로 설명하고 [CWE-674](https://cwe.mitre.org/data/definitions/674.html)에 매핑한다. 관찰한 stack과 일치한다.

여기서 첫 결론은 정직하게 적어야 했다. 목표 취약점은 재현했지만 10분 AFL 캠페인이 crash 입력을 자체 생성한 것은 아니었다. 그래서 당시에는 완료로 세지 않았다.

### 정식 재실행

공개 PoC를 corpus에 넣지 않고 과제 제공 `helloworld.pdf` 678바이트에서 다시 시작했다. PDF 구조 탐색을 빠르게 하기 위해 취약점 입력이 아닌 [AFL++ 일반 PDF dictionary](https://raw.githubusercontent.com/AFLplusplus/AFLplusplus/stable/dictionaries/pdf.dict)를 추가하고, 서로 다른 고정 seed를 가진 12개 인스턴스를 동기화했다.

합계 567,979회 실행 후 slave10이 자신의 45,331번째 실행, AFL time 약 417초에 SIGSEGV 입력을 저장했다. 전체 캠페인의 새 corpus 합계는 7,298개였고 한 인스턴스의 최대 edge 수는 4,093이었다.

```text
id:000000,sig:11,src:000800,time:416909,
execs:45331,op:havoc,rep:2
```

AFL 생성 입력은 656바이트, SHA-256은 `6dc70b49...bb0505d`로 공개 참조 PoC와 달랐다. `afl-tmin`으로 59바이트까지 줄인 뒤에도 SIGSEGV가 유지됐다.

```text
Parser::getObj → XRef::fetch → Object::fetch
→ Dict::lookup → Parser::makeStream → Parser::getObj → ...
```

최소 PoC의 GDB stack은 위 순환을 반복했다. 이는 [CVE-2019-13288](https://nvd.nist.gov/vuln/detail/CVE-2019-13288)의 `Parser::getObj()` 무한 재귀 설명과 일치한다. 이 결과부터 Exercise 1을 정식 완료로 판정했다.

## 2단계 — tcpdump에서 버전을 먼저 의심한 이유

Exercise 3 문서는 tcpdump 4.9.2에서 CVE-2017-13028을 찾도록 안내한다. 그런데 [CVE 레코드](https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2017-13028)는 “tcpdump before 4.9.2”가 영향받는다고 적고, tcpdump [CHANGES](https://github.com/the-tcpdump-group/tcpdump/blob/master/CHANGES)도 4.9.2에 이 수정이 들어갔다고 말한다.

그래서 먼저 교재 그대로 4.9.2를 ASan/AFL++로 빌드했다. BOOTP 중심 seed로 10분 동안 53,668회 실행했지만 crash와 timeout은 모두 0이었다. 이것은 버전 불일치 가설과 맞았다.

다음으로 4.9.1을 같은 방법으로 빌드하고 업스트림이 추가한 [93바이트 BOOTP 회귀 PCAP](https://github.com/the-tcpdump-group/tcpdump/commit/66e22961b30547e9a8daa1f0e8dc9fbe6e2698fa)을 실행했다.

회귀 PCAP을 그대로 seed로 쓰면 dry run에서 즉시 crash가 나므로, caplen을 56바이트로 늘리고 3바이트를 패딩해 먼저 무크래시 seed를 만들었다. AFL++ deterministic mode(`-D`)는 이 seed를 변이해 4,140번째 실행, 약 30초에 첫 crash를 저장했다. 심볼화한 결과는 다음과 같았다.

```text
ERROR: AddressSanitizer: heap-buffer-overflow
#1 bootp_print print-bootp.c:325
SUMMARY: extract.h:144 in EXTRACT_16BITS
```

같은 PCAP은 4.9.2에서 ASan 오류 없이 `[|bootp]`로 안전하게 중단됐다. 공식 bounds check 수정은 [29e5470](https://github.com/the-tcpdump-group/tcpdump/commit/29e5470e6ab84badbc31f4532bb7554a796d9d52)에서 확인할 수 있다.

이 단계의 핵심은 “교재 명령이 실행된다”와 “목표 CVE가 있는 버전이다”가 같은 말이 아니라는 점이다. 퍼징이 아무것도 못 찾을 때는 시간을 더 쓰기 전에 target provenance를 다시 확인해야 한다. 버전을 바로잡은 뒤에는 실제 AFL 생성 crash까지 확보할 수 있었다.

## 3단계 — LibTIFF crash 28개, 최소화, 커버리지, 패치

Exercise 4는 LibTIFF 4.0.4의 `tiffinfo`를 대상으로 한다. 모든 관련 출력 경로를 넓히기 위해 교재처럼 `-D -j -c -r -s -w` 옵션을 사용했고, ASan 계측 바이너리를 AFL++에 연결했다.

```bash
afl-fuzz -m none -i test/images -o out -s 123 -- \
  tiffinfo -D -j -c -r -s -w @@
```

10분 동안 104,771회 실행했고 새 corpus 438개, crash 28개를 저장했다. 대표 crash를 심볼화한 ASan으로 다시 실행한 결과는 다음과 같았다.

```text
ERROR: AddressSanitizer: heap-buffer-overflow
READ of size 2
#1 _TIFFPrintField tif_print.c:127
#2 TIFFPrintDirectory tif_print.c:641
SUMMARY: ... in fputs
```

1바이트로 할당된 ASCII 필드에 NUL 종료가 보장되지 않아 `fputs()`가 heap 경계를 넘어 읽었다. [CVE-2016-9297의 upstream 패치](https://github.com/vadz/libtiff/commit/30c9234c7fd0dd5e8b1e83ad44370c875a0270ed) 설명과 일치한다. ASan은 heap/stack/global out-of-bounds와 use-after-free 등을 탐지하는 도구이며, 첫 오류에서 종료해 stack을 제공한다는 점은 [공식 문서](https://clang.llvm.org/docs/AddressSanitizer.html)에 설명돼 있다.

`afl-tmin`으로 166바이트 입력을 150바이트로 줄였다. 줄인 뒤에도 `_TIFFPrintField()`의 동일한 heap-buffer-overflow가 발생했다.

### PoC 커버리지

GCC `--coverage`로 별도 빌드를 만들고 최소 PoC를 한 번 실행한 후 LCOV HTML을 생성했다.

- lines: 8.9% (1,046 / 11,796)
- functions: 14.8% (83 / 560)

커버리지는 높을수록 무조건 좋은 점수가 아니라 “이 입력이 실제로 어느 코드를 통과했는가”를 확인하는 지도였다.

### 패치도 의심해야 한다

공식 patch를 4.0.4 tarball에 그대로 적용했더니 `patch`가 offset을 이용해 hunk를 인접한 `UINT8` case에 넣었다. 명령은 일부 성공했지만 취약점은 그대로였고 같은 ASan crash가 재현됐다.

`C16_ASCII`와 `C32_ASCII` case에 NUL 종료 보정이 들어가도록 문맥을 수정해 다시 빌드했다. 그 뒤 같은 150바이트 PoC는 포맷 경고를 출력했지만 ASan 오류는 발생하지 않았다. “patch applied”가 아니라 “same PoC no longer crashes”가 완료 조건이어야 한다.

## 마무리

정식 절차로 완료한 세 문제는 Xpdf, tcpdump, LibTIFF다. 이를 통해 만든 최종 triage 흐름은 다음과 같다.

1. 고정 random seed로 캠페인을 재현 가능하게 만든다.
2. crash, hang, 단순 slow input을 분리한다.
3. GDB/ASan stack으로 root cause 함수와 행을 고정한다.
4. 공식 CVE 영향 버전과 upstream commit을 대조한다.
5. `afl-tmin`으로 입력을 줄인다.
6. coverage로 도달 경로를 확인한다.
7. 수정 빌드에 같은 PoC를 재실행한다.

결과적으로 가장 큰 수확은 crash 28개가 아니라, 버전·timeout·patch 성공 로그를 그대로 믿지 않고 증거 체인을 끝까지 확인한 과정이었다.
