# LG유플러스 고객인증시스템(CAS) 개인정보 유출 처분사례: ISMS-P 통제 미흡 및 재발방지 보고서

## 1. 결론 요약

본 보고서는 개인정보보호위원회가 2023년 7월 12일 의결한 LG유플러스 개인정보 유출 처분사례를 대상으로 한다. 공식 발표에 따르면 유출이 확인된 개인정보는 중복 제거 기준 29만 7,117건이며, 휴대전화번호·성명·주소·생년월일 등을 포함한 26개 항목이었다.[^1] 개인정보위는 과징금 68억 원, 과태료 2,700만 원 및 시정명령을 의결하였다.[^1]

사건의 핵심은 외부 침입 하나가 아니라, 노후화된 고객인증시스템(CAS)을 대상으로 **자산·취약점·보안장비·악성코드·테스트 데이터·권한·로그·거버넌스**의 방어선이 동시에 약화된 관리체계 실패라는 점이다. 따라서 재발방지의 우선순위도 단순 장비 도입이 아니라 (1) 개인정보 처리 자산과 데이터 흐름의 재식별, (2) 운영·개발·검수 환경의 분리 및 테스트 데이터 통제, (3) 권한·로그·이상행위 탐지의 폐루프 운영, (4) CPO와 경영진의 이행책임 및 증적화를 구축하는 데 둔다.

> 분석 구분: 사건 사실과 처분 내용은 각주로 제시한 공적 자료에 근거한다. ISMS-P 매핑과 통제 설계는 공개된 ISMS-P 기준의 영역 체계에 사건 사실을 대조한 **분석자의 심사 관점 해석**이며, 실제 인증심사에서는 적용 시점의 고시 및 세부점검항목 원문으로 항목번호·적용범위를 최종 확인해야 한다.

## 2. 사례 선정 및 사건 개요

### 2.1 선정 이유

이 사례는 인증·고객관리 성격의 핵심 시스템에서 기술적 보호조치와 운영 통제가 함께 실패한 사례다. 개인정보위는 CAS의 운영체제, DBMS, 웹서버, WAS 등 상용 소프트웨어 대다수가 유출 추정 시점(2018년 6월)을 기준으로 단종 또는 기술지원 종료 상태였고, 침입차단·침입방지·웹방화벽은 설치되지 않았거나 정책이 제대로 적용되지 않았다고 밝혔다.[^1] 이에 따라 취약점 관리, 공개서버 보안, 접근통제, 변경관리, 개인정보 보유·파기, 사고대응 전반을 한 사례에서 연결할 수 있다.

## 4. 처분 근거와 ISMS-P 관점 매핑

개인정보 보호법 제29조는 개인정보처리자에게 내부 관리계획, 접속기록 보관 등을 포함한 기술적·관리적·물리적 안전조치를 요구한다.[^3] 또한 제34조는 유출 등을 알게 된 때 지체 없이 정보주체에게 통지하도록 정한다.[^4] 당시 사고의 상세 법조문 적용은 처분서 원문으로 최종 확인해야 하나, 개인정보위의 발표 사실은 제29조상 안전조치 의무와 제34조상 통지 의무의 대표적 위험 시나리오에 직접 대응한다.

ISMS-P는 관리체계 수립·운영(16개), 보호대책 요구사항(64개), 개인정보 처리단계 요구사항(21개)으로 구성되며, 보호대책에는 인증·권한관리, 접근통제, 개발보안, 시스템·서비스 운영관리, 시스템·서비스 보안관리, 사고 예방·대응이 포함된다.[^5] 아래 표는 이 공개 체계를 기준으로 한 심사 매핑이다.

## 5. 근본원인 분석

### 5.1 5-Why 요약

**왜 개인정보가 유출될 수 있었는가?** 외부 침입에 취약한 노후 CAS와 보안정책 미적용 상태가 존재했고, 탐지·차단·추적 통제가 충분히 작동하지 않았다.

**왜 탐지·차단·추적이 작동하지 않았는가?** 웹셸 점검·IPS 탐지정책·대량 반출 기록·이상행위 점검이 누락되거나 실효성 있게 운영되지 않았다.

**왜 누락이 장기간 지속됐는가?** 자산 수명, 보안장비 정책, 테스트 데이터, 권한, 로그를 하나의 개인정보 위험 레지스터로 묶어 소유자·기한·검증자를 관리하지 못했다는 해석이 합리적이다. 이는 공식 발표가 여러 통제 영역의 장기 미흡과 저조한 투자·노력 부족을 함께 지적한 데 근거한다.[^1]

**왜 관리체계가 교정하지 못했는가?** CPO 권한, 전문 조직, 내부관리계획, 정기 점검과 경영진 개선 의사결정의 연결이 약했을 가능성이 크다. 이는 개인정보위가 같은 항목의 강화를 시정명령했다는 사실에서 도출한 분석 판단이다.[^1]

### 5.2 통제 설계상 핵심 교훈

1. **인증 취득과 운영 실효성은 다르다.** 정책·장비 보유가 아니라 적용 범위, 예외 만료, 로그, 조치 티켓으로 운영을 증명해야 한다.
2. **개발·검수 환경도 개인정보 처리 시스템이다.** 운영 데이터가 있으면 데이터 흐름도, 접근통제, 로그, 보유기간, 파기 대상에 포함한다.
3. **대량 반출은 별도 위험 시나리오로 모델링해야 한다.** 관리자 정상권한을 통한 대량 조회·다운로드·전송도 유출 경로가 될 수 있으므로 임계치, 승인, 탐지와 사후 검토를 분리 설계한다.
4. **유출통지는 사고대응의 부속 단계가 아니다.** 활성·해지·휴면 등 대상자 세그먼트별 연락처·발송 수단·대체통지 기준을 사전에 시험해야 한다.

### 6.2 대량 개인정보 반출 탐지 기준 예시

임계값은 서비스의 정상 기준선, 개인정보 종류, 계정 역할을 반영해야 하며 아래 값 자체를 보편 기준으로 사용해서는 안 된다. 개인정보위도 크리덴셜 스터핑 판단에서 동일 IP 시도 건수, 평상시 대비 총 시도 건수, 로그인 성공률과 서비스 특성 등을 종합 고려한다고 설명한다.[^6] 같은 원칙을 대량 조회·반출 탐지에도 적용한다.

| 탐지 시나리오 | 기준선 대비 지표 | 자동 조치 | 사람의 검토 |
|---|---|---|---|
| DB 대량 조회 | 사용자·직무별 시간당 조회량의 3σ 초과 또는 고정 임계치 초과 | 고위험 계정 세션 추가인증/일시 중지 | 업무 승인·티켓·대상 필드 확인 |
| 대량 다운로드 | 파일 수/레코드 수/용량 급증, 압축·암호화·외부 전송 연계 | DLP 차단 또는 격리 | 반출 목적·승인·수신처 검증 |
| 비정상 시간/위치 | 평소와 다른 시간대·국가·단말·점프호스트 | 조건부 접근 차단 | 계정탈취 여부·근무 사실 확인 |
| 권한 상승 후 조회 | 권한부여 직후 민감 테이블 대량 접근 | 승인 없는 권한 자동 회수 | 긴급권한 사후승인 검토 |

### 6.3 개발·검수 데이터 표준

1. **기본값은 합성 데이터**로 한다. 테스트 목적이 개인 식별성과 무관하면 운영 데이터의 사본을 만들지 않는다.
2. 실데이터가 불가피하면 DPO·자산소유자·개발책임자의 사전승인을 받고, 목적·항목·건수·보유기한·접근자를 대장에 기록한다.
3. 직접식별자와 준식별자 모두를 위험기반으로 마스킹/치환한다. 단순 일부 마스킹만으로 재식별 위험이 사라진다고 보지 않는다.
4. 개발·검수망은 운영망과 분리하고, 운영 DB의 상시 연결·공유계정을 금지한다.
5. 테스트 종료일에는 자동파기를 우선 적용하고, 파기 성공 로그와 표본 복구불가 검증을 보관한다.

## 8. ISMS-P 심사 대응 패키지

심사에서는 문서 존재만으로 충분하지 않다. 표본을 따라 **정책 → 절차 → 실제 로그/승인 → 예외 → 점검 → 개선**의 연결성을 보여야 한다. ISMS-P 인증신청 안내도 예비점검 준비사항으로 업무·인증범위 소개와 항목별 이행증적을 요구한다.[^7]

### 8.1 제출/제시 자료 목록

| 패키지 | 최소 구성 | 샘플링 방법 |
|---|---|---|
| 개인정보 처리흐름 | CAS·연계시스템·개발/검수·수탁자·데이터 항목·보유기간·국외이전 여부 | 중요 데이터 1개를 골라 수집부터 파기까지 추적 |
| 자산·EOL | CMDB, 중요도, 소유자, 지원종료일, 예외승인, 조치계획 | EOL 자산 3건의 위험수용과 만료 후 조치 확인 |
| 권한 | 권한매트릭스, HR 연계, 특권계정 목록, 분기 재검토 | 퇴직·부서이동·긴급권한 각 1건 추적 |
| 로그·관제 | 로그 수집범위, 보존정책, SIEM 룰, 경보/티켓, 월간 리뷰 | 대량반출 모의 이벤트를 생성해 경보부터 종결까지 확인 |
| 개발데이터 | 반출승인, 마스킹 검증, 테스트 데이터 대장, 자동파기 로그 | 종료된 프로젝트 2건에서 잔존 데이터 부재 확인 |
| 취약점·악성코드 | 스캔 결과, 패치·예외, EDR/FIM, 웹셸 점검, 정책 배포이력 | 고위험 취약점 1건 및 웹셸 알림 1건의 조치 확인 |
| 사고대응 | 역할표, 훈련계획/결과, 신고·통지 런북, 개선조치 | 해지자 연락처를 포함한 모의 통지 훈련 결과 확인 |
| 거버넌스 | CPO 권한, 이사회/경영진 보고, 예산·인력, 내부감사 | 고위험 이슈가 예산·완료 검증까지 연결되는지 확인 |

### 8.2 심사 질의와 답변 구조 예시

**질의:** 개발 환경에 실데이터가 있습니까?  
**답변 구조:** "원칙적으로 합성 데이터를 사용합니다. 실데이터 예외는 `TD-YYYY-NNN` 대장으로 목적·항목·건수·접근자·만료일을 관리하며, 이 표본의 승인서·마스킹 검증·접근기록·자동파기 로그를 제시하겠습니다."

**질의:** 대량 개인정보 반출을 어떻게 탐지합니까?  
**답변 구조:** "DB감사·DLP·SIEM에서 역할별 기준선을 적용합니다. 경보 `EXF-###`가 생성되면 SOC가 15분 내 분류하고, 해당 티켓에 승인 여부·데이터셋·수신처·종결근거를 남깁니다. 최근 3개월 표본과 월간 룰 성능 검토서를 제시하겠습니다."

**질의:** EOL 자산을 왜 운영하고 있습니까?  
**답변 구조:** "현재 EOL 자산은 목록화되어 있으며 원칙적으로 교체합니다. 불가피한 경우에는 종료일, 망분리·가상패치·강화 모니터링 같은 보완통제, 자산소유자·CISO·CPO 승인, 월간 재검토를 갖춘 기한부 위험수용만 허용합니다."

## 9. 한계와 검증 필요사항

1. 이 보고서는 공개 브리핑을 기반으로 하므로 실제 침투 경로, 개별 법 위반 조문, 세부 과징금 산식은 비공개 처분서와 다를 수 있다. 따라서 외부 제출용 법률의견서로 사용할 때는 개인정보위 심의·의결서 및 적용 시점 법령 원문을 확보해 대조해야 한다.
2. 2023년 처분사례의 관리상태를 2026년 현재 상태로 추정하지 않는다. 본 보고서에서 말하는 개선안은 해당 처분을 재현한 가상 조직의 통제 설계다.
3. ISMS-P 세부 항목은 기준 개정에 따라 달라질 수 있다. 본 보고서는 현재 공개된 ISMS-P 자료실의 2024년 안내서·세부점검항목 공개 사실과 제도소개상 영역 체계를 기준으로 작성했다.[^5][^8]
