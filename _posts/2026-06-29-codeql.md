# CodeQL로 소스코드 취약점 탐지하기

> CodeQL의 동작 원리를 이해하고, TaintTracking을 활용해 SQL Injection과 Command Injection을 탐지해보는 실습 기록

---

## CodeQL이란?

**CodeQL**은 GitHub에서 개발한 **정적 분석(SAST) 엔진**이다.  
일반적인 grep이나 시그니처 기반 스캐너와 달리, 소스코드를 **관계형 데이터베이스**로 변환한 뒤 SQL과 유사한 전용 쿼리 언어 **QL**로 취약점 패턴을 질의하는 방식이다.

```
소스코드 → [CodeQL 빌드] → .db (CodeQL Database) → [QL 쿼리 실행] → 결과(alert)
```

GitHub Advanced Security(GHAS)의 코드 스캐닝 기능이 내부적으로 CodeQL을 사용한다고 한다.

---

## 1. 핵심 원리

### 1-1. CodeQL Database 구조

CodeQL은 분석 대상 코드를 빌드하면서 다음 정보를 추출해 DB화한다.

| 구성요소 | 설명 |
|---|---|
| **AST (Abstract Syntax Tree)** | 소스 파싱 결과, 구문 구조 |
| **CFG (Control Flow Graph)** | 실행 흐름, 분기/루프 |
| **DFG (Data Flow Graph)** | 값이 어떻게 전파되는지 |
| **Call Graph** | 함수 호출 관계 |

이 정보들이 `.db` 디렉터리 안에 **관계(relation) 테이블** 형태로 저장된다.  
예를 들어 `BinaryExpr` 테이블은 아래와 같이 정의된다.

```
BinaryExpr.location = 0   ← 코드 위치 (파일, 줄번호)
BinaryExpr.left     = 2   ← 왼쪽 피연산자
BinaryExpr.op       = 3   ← 연산자 (Add, Sub, Mult ...)
BinaryExpr.right    = 4   ← 오른쪽 피연산자
```

### 1-2. TaintTracking

CodeQL의 핵심 기능으로, **Source(입력) → Sink(위험 지점)** 까지 데이터가 흐르는 경로를 자동으로 추적한다.

```
[Source] sys.argv (사용자 입력)
    ↓  sys.argv[1]  (Subscript)
    ↓  username     (변수 할당)
    ↓  query        (문자열 연결로 오염 전파)
[Sink]  conn.execute(query) → SQL Injection!
```

단순 grep과 달리 값이 **변수를 거치거나 문자열 연결로 변형되어도** 오염이 유지된다고 추적한다.

### 1-3. QL 쿼리 구조

```
from [타입] [변수]   // 분석할 요소 선언
where [조건]         // 매칭 조건
select [출력]        // 결과 출력
```

## 2. 환경 세팅 (Windows + VS Code)

### 2-1. CodeQL VS Code 확장 설치

`Ctrl+Shift+X` → `CodeQL` 검색 → **GitHub Security Lab** 설치

CLI가 자동 설치되지만 PATH에 자동 등록되지 않으므로 수동으로 추가해야 한다.

```powershell
# CLI 경로 탐색
Get-ChildItem -Path "$env:USERPROFILE\.vscode" -Filter "codeql.exe" -Recurse -ErrorAction SilentlyContinue | Select-Object FullName

# PATH 등록
[System.Environment]::SetEnvironmentVariable(
  "Path",
  $env:Path + ";C:\Users\[사용자명]\AppData\Roaming\Code\User\globalStorage\github.vscode-codeql\distribution1\codeql",
  "User"
)
```

VS Code 재시작 후 확인:

```powershell
codeql version
# CodeQL command-line toolchain release 2.25.6
```

### 2-2. qlpack.yml 설정

```yaml
# queries/qlpack.yml
name: my-python-queries
version: 0.0.1
dependencies:
  codeql/python-all: "*"
```

```powershell
codeql pack install queries/
```

> **주의**: VS Code에서 쿼리를 실행하려면 `queries/` 폴더 자체를 `File → Open Folder`로 열어야 qlpack이 인식된다.

## 3. 실습

### 3-1. 분석 대상 코드

```python
# vuln_app.py

import sqlite3
import os
import sys

# 취약점 1: SQL Injection
def get_user(username):
    conn = sqlite3.connect('users.db')
    query = "SELECT * FROM users WHERE name = '" + username + "'"  # ❌
    result = conn.execute(query)
    return str(list(result))

# 취약점 2: Command Injection
def ping(host):
    output = os.popen("ping -c 1 " + host).read()  # ❌
    return output

if __name__ == '__main__':
    get_user(sys.argv[1])
    ping(sys.argv[2])
```

### 3-2. CodeQL Database 생성

```powershell
codeql database create ./vuln_db --language=python --source-root=.
# Successfully created database at C:\Users\jinse\codeql-lab\vuln_db
```

### 3-3. SQL Injection 탐지 — TaintTracking

`sys.argv` (Source) → `conn.execute()` (Sink) 경로를 TaintTracking으로 추적한다.

```
/**
 * @name SQL Injection via TaintTracking
 * @description 사용자 입력이 SQL 쿼리까지 오염된 채로 전달됨
 * @kind path-problem
 * @problem.severity error
 * @id python/sql-injection-taint
 */

import python
import semmle.python.dataflow.new.DataFlow
import semmle.python.dataflow.new.TaintTracking

module SqlInjConfig implements DataFlow::ConfigSig {

  // Source: sys.argv (사용자 입력)
  predicate isSource(DataFlow::Node node) {
    exists(Attribute attr |
      attr.getName() = "argv" and
      node.asExpr() = attr
    )
  }

  // Sink: execute()의 첫 번째 인자
  predicate isSink(DataFlow::Node node) {
    exists(DataFlow::CallCfgNode call |
      call.getFunction().(DataFlow::AttrRead).getAttributeName() = "execute" and
      node = call.getArg(0)
    )
  }
}

module SqlInjFlow = TaintTracking::Global<SqlInjConfig>;
import SqlInjFlow::PathGraph

from SqlInjFlow::PathNode source, SqlInjFlow::PathNode sink
where SqlInjFlow::flowPath(source, sink)
select sink.getNode(), source, sink,
  "SQL Injection: $@ 에서 출발한 입력이 SQL 쿼리까지 오염된 채 전달됨",
  source.getNode(), "사용자 입력"
```

**터미널 실행 결과:**

![SQL Injection TaintTracking 터미널 결과](/Hercent.github.io/assets/img/codeql-sqli-terminal.png)

`edges` 테이블이 오염 전파 경로를 보여준다:

```
sys.argv (Attribute)
  → sys.argv[1] (Subscript)
  → username
  → query
  → conn.execute(query)  ← Sink
```

**VS Code 실행 결과:**

![SQL Injection VS Code 결과](/Hercent.github.io/assets/img/codeql-sqli-vscode.png)

### 3-4. Command Injection 탐지 — TaintTracking

```
/**
 * @name Command Injection via TaintTracking
 * @description 사용자 입력이 OS 명령까지 오염된 채로 전달됨
 * @kind path-problem
 * @problem.severity error
 * @id python/cmd-injection-taint
 */

import python
import semmle.python.dataflow.new.DataFlow
import semmle.python.dataflow.new.TaintTracking

module CmdInjConfig implements DataFlow::ConfigSig {

  predicate isSource(DataFlow::Node node) {
    exists(Attribute attr |
      attr.getName() = "argv" and
      node.asExpr() = attr
    )
  }

  predicate isSink(DataFlow::Node node) {
    exists(DataFlow::CallCfgNode call |
      call.getFunction().(DataFlow::AttrRead).getAttributeName() = "popen" and
      node = call.getArg(0)
    )
  }
}

module CmdInjFlow = TaintTracking::Global<CmdInjConfig>;
import CmdInjFlow::PathGraph

from CmdInjFlow::PathNode source, CmdInjFlow::PathNode sink
where CmdInjFlow::flowPath(source, sink)
select sink.getNode(), source, sink,
  "Command Injection: $@ 에서 출발한 입력이 OS 명령까지 오염된 채 전달됨",
  source.getNode(), "사용자 입력"
```

**터미널 실행 결과:**

![Command Injection TaintTracking 터미널 결과](/Hercent.github.io/assets/img/codeql-cmdi-terminal.png)

SQL Injection과 다르게 `host`가 변수를 거치지 않고 `BinaryExpr`에 직접 전달되는 경로가 추적된다:

```
sys.argv (Attribute)
  → sys.argv[2] (Subscript)
  → host
  → "ping -c 1 " + host (BinaryExpr)  ← Sink
```

**VS Code 실행 결과:**

![Command Injection VS Code 결과](/Hercent.github.io/assets/img/codeql-cmdi-vscode.png)

Path 4 steps로 `vuln_app.py:14:23` 정확히 탐지되었다.

## 4. SQL Injection vs Command Injection 경로 비교

TaintTracking이 두 취약점의 오염 전파 구조 차이를 정확히 잡아낸 것을 확인할 수 있다.

| | SQL Injection | Command Injection |
|---|---|---|
| Source | `sys.argv` | `sys.argv` |
| 경유 | `username` → `query` (변수 2개) | `host` (변수 1개) |
| Sink 직전 | `query` 변수 | `BinaryExpr` (`"ping -c 1 " + host`) |
| Path steps | 5 | 4 |

## 5. 실습 중 마주친 트러블슈팅

| 문제 | 원인 | 해결 |
|---|---|---|
| `codeql` 명령어 인식 안 됨 | VS Code 확장이 PATH 자동 등록 안 함 | 수동으로 PATH 등록 후 재시작 |
| `could not resolve module` | qlpack.yml 없음 | `qlpack.yml` 생성 + `pack install` |
| VS Code에서 쿼리 실행 실패 | workspace 루트가 queries 폴더가 아님 | queries 폴더를 `Open Folder`로 열기 |
| `concat` 변수명 에러 | QL 예약어 충돌 | 변수명을 `binop`으로 변경 |
| TaintTracking Source 미탐지 (Flask) | Flask 모델링이 현재 버전과 불일치 | `sys.argv` 기반 예제로 변경 |
| DB 락 에러 | VS Code가 DB를 점유 중 | VS Code 종료 후 터미널에서 실행 |

## 6. CodeQL의 한계

- **비즈니스 로직 취약점 탐지 불가**: "쿠폰은 1개만 써야 한다"처럼 기획 의도를 벗어난 취약점은 코드 구조상 문제가 없어 정적 분석으로 탐지할 수 없다.
- **프레임워크 모델링 의존**: Flask, Django 등 프레임워크의 Source/Sink가 공식적으로 모델링되어 있지 않으면 직접 QL로 구현해야 한다. 실제로 이번 실습에서 Flask `request.args.get()`이 TaintTracking Source로 인식되지 않아 예제를 `sys.argv`로 변경해야 했다.

## 7. grep vs CodeQL

| 항목 | grep / 정규식 | CodeQL |
|---|---|---|
| 분석 수준 | 텍스트 패턴 | AST + 의미론적 분석 |
| 데이터 흐름 추적 | ❌ 불가 | ✅ Source → Sink 추적 |
| 함수 간 분석 | ❌ 불가 | ✅ 인터프로시저 분석 |
| 변형된 값 추적 | ❌ 불가 | ✅ TaintTracking으로 추적 |
| False Positive | 높음 | 낮음 |
| 학습 비용 | 낮음 | 중~높음 |
